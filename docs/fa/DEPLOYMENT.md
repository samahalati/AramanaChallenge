# استقرار، دسترس‌پذیری بالا (HA)، CI و تست بار

هر چه اینجا آمده روی نمونه‌ی اولیه اجرا و اندازه‌گیری شده (عددها از اجرای واقعی‌اند)؛ آنچه راستی‌آزمایی **نشده** در پایان آمده است.

## ۱. سه روش اجرا

| حالت | دستور | پایگاه‌داده | کاربرد |
|---|---|---|---|
| توسعه‌ی محلی | `python manage.py runserver` + `npm run dev` | فایل SQLite | توسعه، دمو |
| کانتینر تکی | `docker build -t aramana . && docker run -p 8000:8000 aramana` | SQLite داخل ایمیج (داده‌ی دمو آماده) | دموی سریع |
| **پشته‌ی تکثیرشده** | `docker compose up -d --build` | PostgreSQL 16 | شبیه تولید (پایین) |

## ۲. پشته‌ی تکثیرشده (`docker-compose.yml`)

```
                 ┌──────────┐      ┌─ replica ۱ برنامه (gunicorn با ۲ worker) ─┐
 مرورگر ──8080─▶│  nginx   │─────▶│                                            │──▶ PostgreSQL 16
                 │ (lb)     │      └─ replica ۲ برنامه (gunicorn با ۲ worker) ─┘     (volume: pgdata)
                 └──────────┘   بررسی سلامت؛ replica ازکارافتاده کنار گذاشته می‌شود
```

```bash
export SECRET_KEY=$(python3 -c "import secrets;print(secrets.token_urlsafe(48))")   # برای همه‌ی replicaها یکسان (JWT را هر replica راستی‌آزمایی می‌کند)
export POSTGRES_PASSWORD=$(python3 -c "import secrets;print(secrets.token_urlsafe(18))")
docker compose up -d --build              # db ← init (مهاجرت + داده‌ی دمو، یک بار) ← ۲ replica ← nginx
docker compose up -d --scale app=3        # افزودن replica
open http://localhost:8080                # compliance@aramana.test / Demo!2345
```

نکته‌های طراحی که replicaها را قابل‌جایگزینی می‌کند:

* **برنامه بدون حالت.** نه نشست در حافظه، نه فایل محلی: JWT با `SECRET_KEY` مشترک امضا می‌شود؛ حساب‌ها، شمارنده‌ی قفل ورود، شمارنده‌ی محدودیت نرخ، هشدارها و زنجیره‌ی حسابرسی در PostgreSQL هستند. حسابِ تعلیق‌شده در درخواست بعدی توسط *هر* replica رد می‌شود (کاربر در هر درخواست دوباره بارگذاری می‌شود).
* **پروب آمادگی.** `GET /api/health` یک `SELECT 1` اجرا می‌کند و اگر پایگاه‌داده در دسترس نباشد ۵۰۳ می‌دهد؛ compose با آن سلامت replica را می‌سنجد و load balancer در خطای اتصال/۵۰۲/۵۰۳ replica دیگر را امتحان می‌کند.
* **زنجیره‌ی حسابرسیِ بدون رقابت.** `AuditLog.prev_hash` یکتا (`UNIQUE`) است: دو workerی که یک «ته زنجیره» را بخوانند نمی‌توانند هر دو بنویسند – بازنده روی ته جدید دوباره تلاش می‌کند (`core/audit.py`، تست `test_audit_append_survives_a_lost_race`). بدون این، با بیش از یک worker زنجیره‌ی هش دوشاخه می‌شد.
* **init یک‌بار‌مصرف.** `init` فقط وقتی پایگاه‌داده خالی است مهاجرت و seed می‌کند؛ replicaها منتظرش می‌مانند.
* **بدون راز در ایمیج.** `.dockerignore` همه‌ی `.env`ها، پایگاه‌داده‌ی محلی و `node_modules` را کنار می‌گذارد.

## ۳. رفتار اندازه‌گیری‌شده (`backend/scripts/loadtest.py`)

آزمایش: یک ماشین (sandbox مشترک)، PostgreSQL 16 + ۲ replica × ۲ worker gunicorn + nginx، ۱۶ thread مشتری، ۳۰ ثانیه، بار ترکیبی (۵ نقطه‌ی خواندنی + نوشتن‌های حسابرسی‌شده)، داده‌ی ۴۷ کاربر / ۵٫۱ هزار جلسه.

| اجرا | توان عملیاتی | خطا | تأخیر p50 / p95 | زنجیره‌ی حسابرسی |
|---|---|---|---|---|
| حالت پایدار | **۱۳۰ درخواست/ثانیه** (۳٬۹۲۲ درخواست) | **۰** | ۱۱۲–۱۳۳ / ۲۰۳–۲۲۷ میلی‌ثانیه | `ok` (۲٬۰۱۸ ردیف، نوشته‌شده هم‌زمان توسط ۴ worker) |
| کشتن یک replica (`docker kill`) ۱۰ ثانیه پس از شروع | ۸۹ درخواست/ثانیه | **۱** (همان یک نوشتنِ در حال انجام روی replica کشته‌شده) | ۱۸۶–۲۰۷ / ۲۴۵–۲۷۴ میلی‌ثانیه | `ok` (۳٬۳۶۴ ردیف) |

برداشت: پشته با ازکارافتادن یک replica به کار ادامه می‌دهد؛ درخواستی که روی replica کشته‌شده در حال پردازش بود شکست می‌خورد (POSTها خودکار تکرار نمی‌شوند – تکرارپذیر نیستند)، بقیه‌ی درخواست‌ها با توان کمتر توسط replica زنده پاسخ داده می‌شوند. این‌ها عددهای یک ماشین برای تخمین مرتبه‌اند، **نه** تضمین ظرفیت.

```bash
python backend/scripts/loadtest.py --base http://localhost:8080 --seconds 30 --threads 16   # در صورت هر خطا یا خرابی زنجیره، کد خروج ۱
```

## ۴. «HA» در اینجا یعنی چه – و یعنی چه نه

| پوشش‌داده‌شده (بالا راستی‌آزمایی شد) | پوشش‌داده‌نشده (نیازمند زیرساخت بیرون از این مخزن) |
|---|---|
| چند replica یکسان پشت load balancer؛ از دست رفتن یکی تحمل می‌شود | **پایگاه‌داده اینجا یک نمونه است.** تولید: PostgreSQL مدیریت‌شده با standby (چند-AZ)، failover خودکار، پشتیبان PITR و بازیابیِ آزموده‌شده |
| چرخش با بررسی سلامت، راه‌اندازی مجدد خودکار (`restart: unless-stopped`) | خودِ load balancer تکی است؛ تولید: LB مدیریت‌شده / دو LB با IP مجازی، پایان TLS، WAF |
| نویسنده‌های هم‌زمان نمی‌توانند زنجیره‌ی حسابرسی را خراب کنند | چند-منطقه‌ای، تمرین بازیابی از فاجعه، روش مهاجرتِ بدون قطعی، مقیاس‌پذیری خودکار، تست‌های طولانی‌مدت |
| پیکربندی با متغیر محیطی، بدون راز در ایمیج | مدیر رازها و چرخش کلید (کلید JWT یک متغیر محیطیِ ساده است) |

## ۵. یکپارچه‌سازی پیوسته (`.github/workflows/ci.yml`)

روی هر push به `main` و هر pull request اجرا می‌شود:

| کار | چه چیزی را اجباری می‌کند |
|---|---|
| `backend` (پایتون ۳٫۱۱ / ۳٫۱۲ / ۳٫۱۳) | `ruff` (خطاهای واقعی)، `manage.py check`، هم‌خوانی مهاجرت‌ها با مدل‌ها، **همه‌ی تست‌ها**، کیفیت تشخیص (`evaluate`)، red-team قطعی محافظ‌های LLM (`evaluate_llm`)، و اینکه `docs/openapi.yaml` + `docs/RBAC_MATRIX.md` از کد بازتولید شده باشند (مستندات کهنه ساخت را رد می‌کند) |
| `postgres` | migrate + seed + ارزیابی + همه‌ی تست‌ها روی PostgreSQL 16 |
| `frontend` | `npm ci`، ترجمه‌ی فارسیِ هر متن رابط (`check:i18n`)، ساخت تولید |
| `docker` | ایمیج ساخته می‌شود، بالا می‌آید، `/api/health` را پاسخ می‌دهد، SPA و Swagger را سرو می‌کند و `X-Frame-Options: DENY` می‌فرستد |

ارزیابی زنده‌ی LLM (`evaluate_llm --live`) عمداً در CI **نیست** (کلید می‌خواهد، محدودیت نرخ دارد، قطعی نیست). گردش‌کار به‌صورت محلی گام‌به‌گام اعتبارسنجی شد (هر دستور `run:` اجرا شد)؛ اجراکننده‌ی میزبانی‌شده هنوز آن را اجرا نکرده – اولین push نشانش می‌دهد.
