# Language support (Persian-first, English switch)

**Official brief:** the challenge PDF is written in English and states no language requirement for the UI, documents, README or data. Persian is therefore permitted; the platform is **Persian by default (RTL, Jalali dates, Persian digits)** with an **EN/فا switch** so English-speaking assessors can read it too. Docs exist in both languages (`docs/` and `docs/fa/`).

## Design rule: store canonical English, localise when presenting

| Layer | How |
|---|---|
| Database | Canonical English tokens and templates (`failed_login_burst`, `critical`, alert titles…). Scores, levels, statuses and rule logic never depend on the language. |
| Request language | `core.middleware.LanguageMiddleware` reads `Accept-Language` into a `ContextVar` (`core/i18n.py`); responses carry `Content-Language`. |
| Alert text | `detection/i18n.py` (pure Python) holds the Persian catalog for system-generated text; `monitoring/localize.py` applies it at serialisation time (title, indicator labels/notes/values, explanation, recommended action, timeline notes). |
| Vocabulary | `core/i18n.TERMS` (enums, roles, permissions, evidence keys) is served at `GET /api/meta/labels`; the SPA loads it once before first render. |
| API errors | `core/errors.exception_handler` translates messages (exact + regex templates) centrally. |
| Demo data | `seed_demo --lang fa` (default) generates Persian pseudonymous names and free text; `--lang en` keeps the English dataset. |
| Frontend | `src/lib/i18n.js` (`t()`, `pretty()`, `num()`, Jalali `d10/dt`), dictionary `src/lib/fa.js`, RTL via logical CSS properties, Vazirmatn (Farsi digits) font bundled from npm. `npm run check:i18n` fails if a `t("…")` key lacks a translation. |

## LLM assistant in Persian
The evidence pack, prompt, deterministic fallback, input gate and the six output guardrails all work in Persian (`detection/assistant/*`). Replies are normalised before checking (`pack.fold`: NFKC, Persian digits → Latin, ZWNJ/diacritics removed, Arabic ي/ك unified) so look-alike/zero-width tricks and Persian digits cannot bypass the number, tone or identity checks. The red-team suite attacks both languages (`python manage.py evaluate_llm` → `docs/llm_eval.txt`).

## Honest limits
* Guardrails are pattern-based: Persian paraphrases outside the patterns can slip through (the output tone/number checks are a floor, not a proof). The suite is self-authored; it measures regression, not real-world robustness.
* No real model was exercised (no API key in the build environment); Persian answer quality from a real LLM is unmeasured.
* Date *pickers* stay Gregorian (browser-native); all displayed dates are Jalali (UTC).
* Free text typed by users is shown as typed (not translated).
